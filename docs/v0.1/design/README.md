## 1 写第一份设计之前

先回主设计文档 [§4 设计槽位](../README.md#4-设计槽位当前全部未填)，确认要填哪个槽位。
槽位是问题清单，不是大纲——可以合并、可以拆、可以删，但删了要在那里标注原因。

再确认一件事：**这份设计是「本工程的目标」，不是「原工程的做法」。**
如果结论来自归档，页首必须写 `来源：归档 <路径>`，并当新提案重新冻结。不写来源、直接照抄，视为把别人的决定冒充自己的，一律退回。

## 2 文件命名

| 类型 | 命名 | 例 |
|---|---|---|
| 全局设计 | `NN_主题.md`，NN 从 00 起 | `00_愿景与支柱.md`、`01_主循环.md` |
| 系统设计 | `<系统名>设计.md` | `背包系统设计.md` |
| 关卡设计 | `<关卡ID>设计.md` | `level_01设计.md` |
| 内容设计 | `<内容类>_<主题>.md` | `剧情_开场.md` |

规则：
- 一个 FeatureID 一页，或一页覆盖多个功能（页内分节，每节独立写 `FeatureID/版本/来源/状态`）。
- 文件名一旦被 `MODULE_INDEX.md` 引用，**不再改名**。要改先改索引，否则断链门禁会红。
- 不建「最新」「最终」「v2」这类文件名。修订用页内 `r2` 标记，历史靠 Git。

## 3 每份设计必须写清的字段

按 [文档驱动开发规范](../../DOCUMENTATION_STANDARD.md) §3，逐项写，缺项标「未实现」或「待核验」，不许留空：

```
FeatureID / 版本 / 来源 / 状态
目标与范围（不做什么也要写）
Owner 与依赖
输入命令（参数、前置条件、幂等键、错误码）
输出事件 / 查询（payload、产生时机、订阅者）
数据与生命周期（内容ID → 实例 → 持久化 → UI/资产）
拒绝与回滚（失败怎么收口）
正式接入（从启动链到它的具体操作路径）
验收（正常/拒绝/重试/读档；需要表现时给真实渲染证据）
关联开发记录
```

模板：[功能设计模板](../../templates/feature_design.md)。

## 4 冻结与登记

1. 草稿写成，标 `来源：用户设计` 或 `来源：工程提案`，状态「未冻结」。此时代码不得据此开工。
2. 用户确认 → 标 `[用户设计]` + 冻结日期。冻结的是**规则**，不是数值细节；规则改了要重新冻结。
3. 在 [功能契约索引](../MODULE_INDEX.md) 加一行、同步 `feature_registry.json`。
4. 写技术施工页，再施工。
5. 验收通过后才允许标 `complete`。

## 5 状态标记

| 标记 | 含义 |
|---|---|
| `[用户设计]` | 已冻结的目标规则，优先级最高 |
| `[工程提案]` | 建议，未确认前不能覆盖用户设计 |
| `[已实装]` | 正式路径具备，且本文档已按当前代码核对 |

本目录当前这三种标记的数量都是 **0**。

## 6 禁止

- 从归档直接复制设计页过来，改个开头就当本工程设计。→ 必须重写并注明来源。
- 在 `development/` 里写新玩法规则。→ 规则只能进本目录。
- 把代码现状反推成用户设计。→ 代码现状属 `[已实装]`，目标设计属 `[用户设计]`，两者不许混写。
- 同一功能两页都是「主设计」。→ 一个 FeatureID 只有一个主设计，其他页只能引用。
