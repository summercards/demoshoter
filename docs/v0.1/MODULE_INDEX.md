## 0 这张表回答什么

每个进入正式路径的功能，都必须能在这里定位到六件事：**FeatureID、Owner、主设计、技术施工、验收入口、状态**。

它是「谁拥有这个功能、凭什么这么写、怎么证明它对」的唯一索引。设计正文写规则，这张表只写指针和状态，**不复制设计内容**。

完整字段要求见 [文档驱动开发规范](../DOCUMENTATION_STANDARD.md) §3。

## 3 怎么登记第一个功能

顺序：**设计冻结 → 分配 FeatureID → 写这一行 → 补契约 → 施工 → 验收**。
不能先写行再补设计，也不能先写代码再回来编 FeatureID。

### 3.1 行格式（固定六列，缺一列门禁会拒）

| FeatureID | Owner | 主设计 | 技术施工 | 验收 | 状态 |
|---|---|---|---|---|---|
| `<域-主题>` | `<状态事实所有者>` | `<design 下的设计页>` | `<对应技术施工页>` | `verify_<名称>` 或命令 | `development` |

列定义：

| 列 | 写什么 | 不许写什么 |
|---|---|---|
| FeatureID | 大写字母/数字 + 连字符的英文 ID（第一列必须是英文 ID，门禁按它扫描） | 中文名、显示名、会变的词 |
| Owner | **唯一**持有该功能最终状态的服务/数据域 | 人名、团队名、多个所有者 |
| 主设计 | 指向 `design/` 下已冻结的设计页 | 指向施工页或归档 |
| 技术施工 | 当前实现的事实、接口、差距 | 目标设计、计划 |
| 验收 | 形如 `verify_<名称>` 的脚本（必须在 `tests/verification/` 存在且已注册）或一条可执行命令 | 「已通过」「手工验过」 |
| 状态 | `design_only` / `contract_only` / `development` / `partial` / `complete` | 自造状态词 |

### 3.2 状态词含义

| 状态 | 含义 |
|---|---|
| `design_only` | 设计已冻结，无实现，不进运行池 |
| `contract_only` | 接口/契约已写，无正式实现 |
| `development` | 属于当前版本施工范围，尚未形成可验收完整链路 |
| `partial` | 已有正式路径或子链路，但契约列出的某项仍缺 |
| `complete` | 正式路径具备，且有验收证据 |

`complete` 不等于「品质达标」，只等于「这条路能走通」。

### 3.3 同步登记表

新增一行的同时，`feature_registry.json` 的 `features` 数组要加一条对应记录，字段：

```
feature_id / owner / design_docs[] / development_records[] / verification[] / status
```

两边必须一致：ID 集合相同、设计路径相同。门禁会逐项比对，缺一边就红。

## 4 空状态怎么解除

删掉文件顶部那一行标记：

```
<!-- EMPTY-PROJECT-INDEX -->
```

然后按 §3 填表。标记一旦删除，门禁恢复全部严格检查：六列完整、ID 唯一、设计与注册表一致、验收脚本存在且已注册。

**留着标记却填了功能行，门禁会直接报错。** 这个标记是「我确认现在没有功能」的声明，不是省事的开关。

## 5 不该写在这里的东西

| 内容 | 该去哪 |
|---|---|
| 玩法规则、数值、公式 | `design/` 的设计页 |
| 实现细节、接口签名、失败码 | 对应技术施工页 |
| 「本轮修了什么」 | `development/` 交付记录 |
| 骨架现有能力 | [骨架能力说明书](../SKELETON_CAPABILITIES.md) |
| 计划、待办、想法 | 开发记录里的「未做」段，或主设计文档 §4 的设计槽位 |
| 原工程的功能清单 | 归档。**不搬回来当本工程的功能表** |
