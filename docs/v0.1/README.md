## 0 这份文档现在是什么

本工程是《弹壳风暴2》的**初始化骨架工程**。它有一个能跑起来的 3D 底座、一套完整的工程规范、一批可复用的运行时模块 —— **但没有已确定的玩法**。

所以这份主设计文档现在是**空白骨架**：它只定义「设计应该写在哪、按什么格式写、谁拥有它、怎么算冻结」，**不回答这个游戏是什么**。

> 一句话：**这份文档现在的正确内容是"还没有内容"。**
> 如果发现它开始描述某种具体玩法（搜打撤、爬塔、Roguelike、塔防……），那不是本工程的既定设计，是有人把归档或代码现状当成了目标 —— 必须退回。

原《弹壳风暴2》的全部玩法设计、技术施工、审计与交付记录已整体归档，**不构成本工程的设计依据**：

```
docs/archive/inherited_shellstorm2_2026-10-21/
```

归档说明见该目录 `README.md`。归档里的「七大核心系统」「12 只唯一精英」「78 张塔罗」「单层 7 房远征」等等，**全部是原工程在那个时点的决定，与本工程无关**。

## 2 本工程真实存在什么

**地基存在，玩法未定。** 完整盘点见 [骨架能力说明书](../SKELETON_CAPABILITIES.md)，这里只列结论：

| 类别 | 现状 |
|---|---|
| 启动链 | `StartupLoadingScreen` → `scenes/greybox/GreyboxLevel01.tscn`；标题「弹壳风暴-青春版」 |
| 关卡基座 | 灰盒场景 `instance` 自 `scenes/Dungeon3D.tscn`，继承战斗、背包、奖励、装备事务与存档；几何全部程序化白盒（60×60 m、5 个胶囊敌人、白盒设施占位） |
| 自动加载 | 27 个 Autoload 全部在位（存档、基地、时间、音频、输入、AI、特效池、剧情、画质……） |
| 运行时模块 | `src/` 下 24 个模块目录、约 300 个脚本：玩家状态机、武器装配、背包、敌人 AI、房间/门、存档、UI |
| 美术资产 | `assets/` 约 199 个 glb、228 个 tscn（角色、敌人、道具、部分环境） |
| 已剥离 | `_removed_content/`：Boss 模型、房间组件源、BGM、远征关卡场景等 4670 个文件 |

**这些是"可以用的积木"，不是"已经定下的游戏"。** 例如 `Dungeon3D` 现在能跑「清房间 + 开箱 + 撤离」，那只是因为它是从原工程继承的基座，不代表本工程的目标玩法就是搜打撤。要不要保留这个形状，是设计决定，不是既成事实。

## 3 后续怎么自由发挥

玩法方向由设计者决定，本工程**不预设、不引导、不限制**。可以是完全不同的类型，也可以只复用底座的一部分。

唯一的硬约束是**流程与规范**：

| 优先级 | 依据 | 冲突时 |
|---:|---|---|
| 1 | 用户当轮的明确指令 | 最高 |
| 2 | `docs/v0.1/design/` 中已冻结的目标设计（当前为空） | 覆盖规范中的默认值 |
| 3 | 规范文档：`docs/DOCUMENTATION_STANDARD.md`、`docs/v0.1/关卡接入规范.md`、`docs/v0.1/10_资产与内容规范.md`、`docs/v0.1/11_测试与发布.md` 等 | 不得违反 |
| 4 | 归档文档 `docs/archive/inherited_shellstorm2_2026-10-21/` | **只能参考，不能作依据** |

「自由」的边界只有一条：**任何进入正式路径的玩法，必须先有冻结的设计，再有代码。** 不能先写实现再倒推设计，也不能因为代码里已经存在某个行为就把它写成目标。

## 5 第一份玩法设计怎么写

顺序不可颠倒。这是 `DOCUMENTATION_STANDARD.md` §2 的具体化：

1. **提案。** 在 `design/` 下新建草稿。开头写明 `来源：用户设计` 或 `来源：工程提案`。此时状态是「未冻结」，不具约束力，代码不得据此开工。
2. **冻结。** 用户确认后，把草稿标为 `[用户设计]` 并记录冻结日期。冻结的是**规则**，不是数值细节 —— 数值可以后续调，规则改了要重新冻结。
3. **登记。** 在 [功能契约索引](MODULE_INDEX.md) 增加一行：FeatureID、Owner、主设计、施工、验收、状态；同步 `feature_registry.json`。**FeatureID 一旦分配不再改名。**
4. **写契约。** 按 `DOCUMENTATION_STANDARD.md` §3 的十一个字段补齐：状态所有者、输入命令、输出事件、数据链、失败收口、正式接入、验收标准。
5. **施工与验收。** 先跑基线，再改代码；退出码、预期故障、非预期脚本错误、未执行项分别记录。真实渲染的用例不能算进无头通过。

第 1 步之前什么都没有，是**正常状态**，不是待办积压。

## 6 状态标记

沿用原工程的三色标记，语义不变：

| 标记 | 含义 | 使用边界 |
|---|---|---|
| `[已实装]` | 正式运行路径具备该能力，且**本文档已按当前代码核对** | 仅代码存在但未接入正式入口，不算 |
| `[用户设计]` | 尚未呈现、由设计者明确提出并冻结的目标 | 优先级高于工程提案 |
| `[工程提案]` | 为补齐闭环或可维护性提出的建议 | 未确认前不得覆盖 `[用户设计]` |

本工程当前适用情况：
- `[已实装]` 只应用于**骨架能力**（启动链、Dungeon3D 基座、Autoload、可复用模块），且以 [骨架能力说明书](../SKELETON_CAPABILITIES.md) 的记录为准。
- **`[用户设计]` 数量为 0。** 任何地方出现它，说明设计已经开始，本文件 §1 的表格必须同步更新。

旧文档里的 `[Codex补充]` 在本工程改称 `[工程提案]`，避免把某个工具名写成角色。

## 7 不随玩法变化的工程约束

这些约束来自规范文档，**换什么玩法都要遵守**：

| 约束 | 出处 |
|---|---|
| 先设计后代码；改语义先改设计段 | `docs/DOCUMENTATION_STANDARD.md` §2 |
| 每个功能必须有唯一状态所有者、命令/事件、数据链、失败收口、独立验收入口 | 同上 §3 |
| 运行资产路径**不带版本号**，版本只写 `art_source/`、`asset_manifest.json`、台账与 Prefab 根 `metadata/asset_version` | `AGENTS.md`、`scripts/check_asset_runtime_naming.py` |
| 关卡通用机制按**能力**分支，关卡专属内容按 **ID** 分支，两者不许混 | `docs/v0.1/关卡接入规范.md`、`scripts/check_level_decoupling.py` |
| 美术制作源统一在 `art_source/`，运行导入资源原路径稳定 | `docs/ART_SOURCE_LAYOUT.md` |
| 自动测试必须在 Autoload 启动前隔离用户数据目录 | `AGENTS.md` |
| 存档目录由 `config/custom_user_dir_name` 决定（当前 `ShellStorm2Port`），**不随显示名变化** | `project.godot` 注释 |
| 验收分别记录退出码、预期故障、非预期脚本错误、未执行项 | `docs/DOCUMENTATION_STANDARD.md` §6 |
| 交付前跑 `python3 scripts/check_documentation_contracts.py` 与相关验证 | `AGENTS.md` |

存档格式、资产路径、关卡解耦这三项属于**改了会连带炸一片**的约束。要动其中任何一条，先写设计修订，再改，不许顺手改。

## 8 阅读顺序

第一次进入本工程，按这个顺序读：

1. 本文件（你现在在这里）—— 确认这是空项目。
2. [骨架能力说明书](../SKELETON_CAPABILITIES.md) —— 确认手上有什么积木。
3. [文档驱动开发规范](../DOCUMENTATION_STANDARD.md) —— 确认怎么干活。
4. [功能契约索引](MODULE_INDEX.md) —— 确认当前没有任何功能被登记（空白表就是答案）。
5. [关卡接入规范](关卡接入规范.md) —— 一旦要做关卡，这是唯一入口文档。
6. [设计目录说明](design/README.md) —— 准备写第一份设计时再看。

不需要读的：`docs/archive/inherited_shellstorm2_2026-10-21/`。除非你在排查某个具体技术坑，且已经知道要找什么。

## 9 与归档的关系

| 你想做的事 | 正确做法 | 错误做法 |
|---|---|---|
| 复用原工程的某个系统设计 | 在 `design/` 重写一份，页首注明「来源：归档 XXX」，重新冻结 | 直接链接归档文件当依据 |
| 查原工程某个坑怎么踩的 | 直接搜归档，当技术资料用 | 把归档里的结论当成当前约束 |
| 判断某个功能本工程有没有 | 查 [骨架能力说明书](../SKELETON_CAPABILITIES.md) | 查归档里的「已实装」标记 |
| 找原工程的资产编号 | 查 `assets/registry/` 台账 | 查归档里的设计页转述 |

归档的存在价值只有一个：**少踩已经踩过的坑**。它不是设计债，也不是默认答案。
